# ADR-001：将目录事实、能力与导航意图分离

审计范围为 `main@69d71a9`、版本 `2.5.13`。全程只读；未改文件、未切分支。工作区原有未跟踪 `scripts/`，未触碰。基线验证：`npm test -- --runInBand` 通过，28 个 suite、176 个测试、0 失败；本轮没有用户可见改动，因此未运行构建。

## 1. 执行摘要

- 唯一推荐方向：以 `PhysicalDirectory / DirectorySnapshot` 为当前核心模型，主进程只返回物理事实；能力由共享纯函数派生，视图由显式导航意图决定。
- 不再把 `folder|album` 当互斥领域身份；`contentKind` 仅是派生投影，`primaryView` 必须是场景策略。
- 保留现有 hybrid 的 album-first 主点击行为，但把它固定在 `cardPrimaryClick` 策略中，不再污染收藏类型、相邻序列或目录身份。
- 引入轻量 `SourceRoot + DirectoryRef + NavigationTarget`；不引入 SQLite、全量索引、内容哈希或大规模 TypeScript 迁移。
- 绝对路径降为当前 locator；持久引用采用 `sourceId + relativePath`，但明确承认目录内部重命名仍会使引用失效。
- “随机选相簿支持文件夹”第一阶段选择 A，并改名“随机浏览”：当前层每个可见目录卡片一票，不递归、不抽直属图片。
- 随机池取当前层全部卡片级目录，明确忽略搜索和排序；hybrid 一目录一票，pure folder 进入 browse，photo/hybrid 进入 photoSet。
- 随机袋由 `BrowserPage` 按标签和来源目录持有，跨 Home/Album、前进后退持续，但不跨应用重启。
- 缓存统一为单层 snapshot、有限 TTL、per-key epoch；应用内变更立即失效当前目录及父目录，防止旧扫描回写。
- 未来若出现真正用户自建相簿，必须新增独立 `LogicalAlbum`；本轮不实现，也不恢复 `4737595` 关闭的 approved-root 校验。

最高杠杆点不是改名，而是切断这条错误依赖：

```text
目录事实 → 目录能力 → 场景导航策略 → 页面
```

这样相邻导航、随机、收藏、卡片主点击不再争夺一个全局“主身份”。

### 外部产品事实

共同不变量不是大家都用同一术语，而是：

- Lightroom 的 Folders 反映磁盘层级，而 Collections 是独立逻辑成员关系，Collection Set 只组织 Collection、不直接含照片。[Adobe Folders](https://helpx.adobe.com/lightroom-classic/desktop/manage-catalogs-and-files/create-folders.html)、[Adobe Collections](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/photo-collections.html)
- Apple Photos 的 Album 含媒体且支持多重归属，Folder 用于组织 Album/子 Folder。[Apple Albums](https://support.apple.com/guide/photos/create-and-work-with-albums-pht6d60a1f1/mac)、[Apple Folders](https://support.apple.com/guide/photos/group-albums-in-folders-pht211de0d6/mac)
- digiKam 把 Collection 作为顶层物理 root，把其下所有物理子目录稳定称为 Album；不会因某目录当前有没有直属图片而改变其物理身份，并显式处理本地盘、移动介质和 NAS mount。[digiKam Albums](https://docs.digikam.org/en/left_sidebar/albums_view.html)、[digiKam Collections](https://docs.digikam.org/en/setup_application/collections_settings.html)
- PhotoPrism 与 Immich 都把 folder view 作为文件系统维度，把 Album、Timeline 等作为另一维度。[PhotoPrism Folders](https://docs.photoprism.app/user-guide/organize/folders/)、[Immich Folder View](https://docs.immich.app/features/folder-view/)

不适合照搬的部分是 catalog/index：Lightroom、digiKam、PhotoPrism、Immich 都会持久化或索引媒体记录；Immich 甚至明确把外部文件扫描成资产记录，移动后可能丢失应用内 metadata。[Immich External Libraries](https://docs.immich.app/features/libraries/) 本项目当前不需要承担这套成本。

### 推断

- **相邻导航 bug 迫使全局 primary identity 改变，是错误边界的直接证据。** 相邻序列本来已经用 `canViewAsPhotoSet` 筛选，导航结果也显式进入 album；真正混在一起的是“用户如何进入 AlbumPage”“卡片显示类型”“收藏落在哪个数组”和全局 `getPrimaryView`。`774d5c3` 为恢复一个场景，把全局 card/favorite identity 一并改了。
- `CHANGELOG` 所称“逐个消耗”的不放回，只在同一 hook 实例且 signature 不变时成立。正常 Home、Album、ImageViewer 交互都在一次抽取后重置，因此 A→B→A 可在 C 尚未访问时发生。[CHANGELOG.md:35–38](/Users/clover/Develop/photo-album-viewer6/CHANGELOG.md:35)
- source root 缺失不仅是建模问题，还已造成新窗口 bootstrap、breadcrumb、返回上级、多标签来源归属不一致。
- 删除最后一张直属图片后，父级缓存可能仍把该目录当 album/hybrid，sibling 也可能继续包含它，最长持续到 navigation TTL 过期。
- Favorites 的 revision 检查并非原子 CAS：两个并发 save 可能同时读相同 revision、同时通过、最后写覆盖前写。
- 采样出的 `hasSubAlbums/previewSamples` 目前与精确计数混在同一 DTO。它暂时主要影响展示，但继续扩展后很容易被误用于身份或随机资格。

### 未知

- 实际用户机器上 v1 favorites/session 的历史 shape、无 kind 记录数量和 root 哈希数据。
- 每个磁盘/NAS 的大小写敏感性、symlink 习惯、离线重挂载方式。
- 产品负责人是否希望搜索同时缩小随机池；本方案默认不缩小。
- SourceRoot 是否应严格限制“返回上级”的 UI 边界；本方案默认是导航边界，但不是授权边界。
- 未来是否真的需要任意成员逻辑相簿、跨源搜索、离线浏览或移动后自动重连。

## 4. 方案比较

| 方案 | 优点 | 代价/问题 | 结论 |
|---|---|---|---|
| 继续 `folder|album` 二分并打补丁 | 改动最小；短期可把 folder 加入 random | 内容变化会继续改变身份；primary、收藏、随机、相邻仍互相耦合；legacy 字段继续增长 | 淘汰 |
| 单一 `PhysicalDirectory + facts + derived capabilities + explicit views` | 符合零导入；不需 DB；目录身份稳定；可渐进接适配器；未来逻辑相簿边界清楚 | 需要 shared contract、SourceRoot、持久化迁移和策略拆分 | **推荐** |
| 现在就分离 PhysicalFolder/LogicalAlbum 并引入完整 catalog | 可支持稳定媒体 ID、智能相簿、全局搜索、离线索引 | 扫描/迁移/一致性成本高；与零导入、目录即数据、YAGNI 冲突 | 当前淘汰；满足翻转条件后再采用 |

digiKam 证明“所有物理子目录都稳定叫 Album”也能自洽；但本项目未来若有真正逻辑 Album，这个词会产生新冲突。因此推荐领域层使用 `Directory`，UI 可继续显示“相簿/照片集合”。

## 5. 规范领域模型

### 5.1 SourceRoot 与 DirectoryRef

```js
/** @typedef {Object} SourceRoot */
{
  schemaVersion: 1,
  sourceId: "src_<random-uuid>",       // 跨会话稳定，不由 path/hash 派生
  label: "家庭照片",
  rootPath: "/Volumes/NAS/Photos",     // 当前 locator，不是身份
  sourceGeneration: 3                 // relink/rootPath 变化时递增
}

/** @typedef {Object} DirectoryRef */
{
  sourceId: "src_<random-uuid>",
  relativePath: "2026/旅行/杭州"        // root 为 ""；序列化统一 /
}
```

不变量：

- `relativePath` 不得是绝对路径，不含 `..`，保留原始大小写。
- SourceRoot 是导航上下文，不是 approved-root 授权名单；`4737595` 不变。
- `sourceGeneration` 只用于 cache namespace，不改变 `sourceId`。
- NAS mount/盘符变化只更新 `rootPath`；目录内部 rename/move 会改变 `relativePath`，必须 relink，不能伪称自动稳定。

### 5.2 DirectorySnapshot

```js
/** @typedef {Object} DirectorySnapshot */
{
  contractVersion: 1,
  ref: { sourceId, relativePath },
  locator: { absolutePath },           // IPC 运行期调试/展示；不持久化为身份
  name: "杭州",
  status: "ready",                     // ready | unreadable | missing | sourceOffline
  observedAt: 1780000000000,
  revision: "opaque-main-revision",

  completeness: {
    entries: "complete",               // complete | partial
    directMedia: "complete",
    children: "complete"
  },

  facts: {
    directMediaCount: 42,              // complete 时精确；partial 时仅下界
    childDirectoryCount: 3
  },

  directMedia: [
    { relativePath: "2026/旅行/杭州/001.jpg", name: "001.jpg", size: 1234, mtimeMs: 0 }
  ],

  children: [
    {
      ref: { sourceId, relativePath: "2026/旅行/杭州/自拍" },
      name: "自拍",
      status: "ready",

      facts: { directMediaCount: 8, childDirectoryCount: 0 },
      approximate: {
        coverSamples: ["2026/旅行/杭州/自拍/001.jpg"],
        hasDescendantMedia: "yes",
        observedAt: 1780000000000,
        truncated: false
      }
    }
  ],

  approximate: {
    coverSamples: [],
    hasDescendantMedia: "unknown",     // yes | no | unknown
    observedAt: 1780000000000,
    truncated: true
  }

```

`children` 只能是单层 child fact/ref，不能递归嵌套完整 `DirectorySnapshot`，否则精准失效会退化为“清所有祖先”。

派生能力必须是三值：

```text
directMediaCount > 0                        → canViewDirectMedia = true
directMedia complete 且 count = 0           → false
directMedia partial 且尚未发现图片          → unknown
```

`contentKind='empty'` 只有在 directMedia 和 children 均 complete 且为 0 时成立。

```js

{
```

### 5.4 SavedLocation

```js
/** @typedef {Object} SavedLocation */
{
  id: "saved_<uuid>",
  target: {
    sourceId: "src_<uuid>",
    relativePath: "2026/旅行/杭州",
    viewMode: "photoSet"
  },
  label: "杭州",
  createdAt: 1780000000000,
  presentationCache: {
    coverRelativePath: "2026/旅行/杭州/001.jpg",
```

身份为 `(sourceId, relativePath, viewMode)`，所以同一路径的 browse 与 photoSet 收藏继续共存。`presentationCache` 可 stale，不决定打开方式。

### 5.5 RandomScope / RandomTarget

```js
/** @typedef {Object} RandomScope */
{
  kind: "directoryNavigation",
  sourceDirectory: { sourceId, relativePath },
  candidateSignature: "hash(sorted directory-ref + target-view)"

/** @typedef {Object} RandomNavigationTarget */
{
  kind: "directoryNavigation",
```


### 5.6 字段分类

| 分类 | 字段/例子 | 真相源 |
|---|---|---|
| Canonical fact | status、completeness、直属媒体数、直属子目录数、size、mtime | main 扫描 |
| Locator/reference | SourceRoot.rootPath、DirectoryRef | SourceRoot registry |
| Derived projection | `canViewDirectMedia`、`canBrowseChildren`、`contentKind` | 一个共享纯函数 |
| UI policy | card primary、breadcrumb、random target view | `navigationPolicy` |
| Approximate metadata | descendant media、深层封面、truncated | 独立 approximate 区 |
| Legacy compatibility | type、kind、canOpenAlbum、hasImages、imageCount、childFolders | adapter，禁止新代码消费 |

### 5.7 path 方案比较

| 方案 | 跨平台/NAS | rename/move | 成本 | 结论 |
|---|---|---|---|---|
| 绝对路径主键 | mount、盘符、UNC 变化即失效；大小写/分隔符易重复 | 任意 rename/move 都失效 | 最低 | 仅作为 locator/legacy |
| `sourceId + relativePath` | rootPath 可整体 relink，适合 NAS 重挂载 | source 内部 rename/move仍失效 | 小型 registry | **推荐** |
| 每个目录 App UUID + mutable locator | 理论可追踪 move | 没有 watcher/catalog 就无法更新 locator | 接近 catalog | 当前拒绝 |
| inode/file ID | SMB/NAS/复制/重建/复用不稳定，Windows 模型不同 | 同一文件系统内可能辅助 | 平台特判多 | 仅可作提示 |
| macOS bookmark | macOS 专属授权/定位 token，可能 stale | 有限帮助 | 不跨平台 | 不能作通用身份 |
| content hash | 目录级计算昂贵，内容变更即变，复制会碰撞身份 | 不代表目录身份 | 极高 I/O | 拒绝 |

未来真正的用户相簿应是：

```js
LogicalAlbum { albumId, name, members: MediaRef[] }
```

它与 `PhysicalDirectory` 平行存在，绝不能让“含直属图片的目录”冒充它。本轮不创建该类型的存储或数据库。

|---|---|---|---|---|---|---|
| pure container：0 图、>0 子目录 | 文件夹卡；主点击 browse；无 photo 次入口 | browse 可用；photoSet 不可用 | 一票，结果 browse | 不进入 photo sibling 序列 | 只允许 browse SavedLocation | 若新增直属图，变 hybrid；旧 browse 收藏不变 |

## 7. 随机设计

### A/B/C 比较

| 语义 | 优点 | 代价 | 决定 |
|---|---|---|---|
| A 随机导航节点 | 与“一目录一卡片”一致；一次扫描已有候选；公平单位明确；无递归 | 抽到 folder 后可能还要继续浏览，不能称“随机相簿” | **采用，UI 改名“随机浏览”** |
| B 随机内容集合 | 符合“随机找一套可看照片” | 必须完整枚举唯一 MediaSet；递归 I/O、取消、进度、symlink 环、分支偏置、NAS 延迟 | 暂缓 |
| C folder/photoSet 能力各一票 | 可同时暴露两个 view | hybrid 获两票，概率无业务依据 | 拒绝 |

A 的最强反对意见是：它支持的是“随机目录导航”，不是“随机照片内容”。若产品真正目标是后者，应直接改选 B，而不是把两者混在一个按钮中。

### 明确语义

- 候选：当前来源目录的全部**卡片级、可打开的直属目录节点**，不受搜索过滤影响。
- 搜索：仅影响显示；不改变池、不重置袋。按钮 tooltip 应说明“随机当前文件夹”。
- 排序：不影响概率、不进入 signature。
- hybrid：按 DirectoryRef 去重，一目录一票。
- 当前目录 `directImages`：不参与。
- AlbumPage random：可以抽到 pure folder sibling，并进入 browse。
- prev/next：仍只遍历 `canViewDirectMedia=true` 的 sibling。
- 公平性：每个唯一 DirectoryRef 等概率，不是每个媒体集合或每张图片等概率。
- symlink：第一阶段按显示卡片/lexical DirectoryRef 计票；不按 inode/realpath 静默合并。
- 袋状态：跨 Home/Album、同标签前进后退及标签切换保留；关闭标签清理；不跨应用重启。
- 多标签：即使路径相同也各有独立袋。
- 重置：SourceRoot/来源目录变化，或排序后的 `candidateKey|viewMode` signature 变化。仅排序、搜索、current path 变化、Album 图片 refresh 不重置。
- 候选增删/类型变化：父目录重扫后 signature 改变，开启新一轮。
- stale：仅 missing/类型变化触发父目录强制重扫一次并重抽一次；第二次失败即停止。权限或 NAS offline 不循环重试。

### 候选构建伪代码

```js
/**
 * @returns {RandomNavigationTarget[]}
 */
function buildRandomNavigationTargets(levelSnapshot) {
  const uniqueByDirectory = new Map();

  for (const child of levelSnapshot.children) {
    if (child.status !== 'ready') continue;

    const caps = deriveDirectoryCapabilities(child); // true | false | unknown
    let viewMode = null;

    if (caps.canViewDirectMedia === true) {
      viewMode = 'photoSet'; // 保留当前 hybrid album-first
    } else if (caps.canBrowseChildren === true) {
      viewMode = 'browse';
    }

    if (!viewMode) continue; // empty / unknown / unreadable

    const key = directoryRefKey(child.ref);
    uniqueByDirectory.set(key, {
      kind: 'directoryNavigation',
      candidateKey: key,
      target: { ...child.ref, viewMode }
    });
  }

  return [...uniqueByDirectory.values()]
    .sort((a, b) => a.candidateKey.localeCompare(b.candidateKey));
}
```

### 真正不放回的所有权

```text
BrowserPage
└── randomStateByTabId
    └── tabId
        └── bounded LRU<sourceDirectoryRef, BagState>
```

- `currentDirectoryRef` 不进入 signature。
- 从 AlbumPage 首次建立袋时，当前目录视为本轮已访问。
- draw 时若 remaining 中出现当前目录，消费并跳过，不重建整袋。
- 新一轮 refill 时，若第一项等于 `lastReturnedKey` 且候选数 > 1，交换到后面，避免轮次边界立即重复。
- LRU 只需保留少量来源 scope，例如每标签 8 个；不是持久化 schema。

### stale 执行流程

```text
draw target
  → main resolve/validate target
    → ok：navigate
    → missing / view no longer valid：
         invalidate parent epoch
         force rescan parent once
         rebuild candidates
         draw once more
    → unreadable / sourceOffline / IPC error：
         stop and show precise error
```

### 快捷键

Home 和 Album 的页面级 handler 都应在 `viewerOpen` 时忽略 E/R；Viewer 自己拥有 E=旋转、R=随机图片，并同时覆盖大小写。这样不会依赖事件监听注册顺序。

| Windows 路径与 NAS | 分隔符、盘符、UNC、mount 不稳定 | main 按 path flavor 解析；不全局 lower-case；source root relink；UNC root 止于 share | 保留 originalAbsolutePath | offline 与 missing 分开提示 |
| 外部 rename/move/delete | source-relative 不能自动恢复内部移动 | root move 更新 SourceRoot；子目录移动逐条 relink；不按名字/封面/hash 猜 | legacy absolute 留在 migration journal | 提供“修本条/修整个来源”两种明确操作 |
| approved-root | SourceRoot 可能被误作安全名单 | 明确 SourceRoot 只用于身份/导航；`assertApprovedPath` 决策不改 | 不涉及 | 无 |

旧数据归 root 的默认规则：

1. 只在唯一、segment-boundary 匹配的最长已知 SourceRoot 下自动映射。
2. 多个候选、跨平台 path flavor、路径不存在或 root 不可证明时，保留 `legacyAbsolutePath + unresolved`。
3. 不制造 OS volume/share synthetic SourceRoot，不把猜测标记为迁移成功。

## 13. 反方与翻转条件

### 推荐方案最强的反对意见

`sourceId + relativePath` 只是“比绝对路径更好的 locator”，不是真正稳定实体身份。它不能自动跟踪 source 内部 rename/move；如果未来持续给它叠加 relink、搜索索引、离线 metadata、媒体 UUID，最终可能是在 JSON 文件上重造一个更差的 catalog。

这个反对意见成立，所以必须明确止损线：当前只做 root registry、snapshot 和显式 relink，不做隐藏的目录 UUID/内容匹配系统。

### 会让我改变结论的新事实

出现任一条件，就应重新评估 SQLite/catalog：

- 用户自建逻辑相簿、智能规则或跨目录任意成员关系成为核心功能。
- 要求收藏/相簿在任意目录 rename/move 后自动保持。
- 需要跨 SourceRoot 全局搜索、时间线、去重、人脸、标签或离线浏览。
- NAS/百万文件规模使按需扫描和有限 TTL 无法满足交互性能。
- 需要多设备同步、事务合并或多进程可靠并发写。
- 产品目标从“随机浏览当前层”改为“在整个子树均匀随机一个媒体集合”，此时应选 B 并设计可取消递归/index，而不是扩张 A。
- 只有当产品明确希望 hybrid 因有两个入口而获得双倍概率时，才考虑 C；目前没有这种依据。

### 仍需产品负责人确认的最少问题

1. SourceRoot 默认是否同时作为 breadcrumb/返回上级的 UI 边界？本方案默认“是”，但不作为安全授权边界。
2. 随机是否明确忽略搜索？本方案默认“是”，以换取稳定、可解释、跨页面的一轮。
3. v1 route/session/favorites 的兼容窗口保留多久？建议至少两个 minor 版本，并在删除 adapter 前单独确认。
