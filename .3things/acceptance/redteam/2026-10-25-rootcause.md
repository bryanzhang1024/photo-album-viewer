## 结论

1. **能力上，4.0 不是一次「界面重写」，而是一次带功能删除的界面重写。** 3.13.1 有 9 类用户可见能力在 4.0 被删或降级：多标签页与会话恢复、每标签前进后退、打开文件夹/拖入注册来源、新窗口、面包屑点击与截断、⌘[ ⌘] ⌘↑ ⌘F（及状态栏广告的 ⌘, ⌘W）、列头排序与升降序、收藏的三对象与卡片心形、查看器复制/Finder/键位/右键/滚轮翻页。全部集中在渲染层「接线」，主进程一行没删；旧 renderer 55 个文件与旧测试 38 个文件在最后一个提交里一次性删除（该提交共删 25,937 行），新测试 26 个文件、0 个渲染 `src/ui` 产品组件。
2. **设计稿来源：抽 20 条定稿要求，11 条有用户原话（含「用户确认代理提案」），6 条纯执行方推断，3 条与用户原话/建议冲突。** 最关键的一条是验收判据——用户只选了「每片截图并排 + 关键节点装给我试」，而「同尺寸截图对不上即未完成」是执行方自己写进 `AGENTS.md` 的通过标准；用户选定的「装给我试」在合并 main 前一次也没有发生（预览版在 11:05/11:40/11:47/11:52 装了 4 次，用户 10:47–13:27 没有发过消息）。
3. **根因不是「不够谨慎」，而是谨慎全部落在静态方案上。** 确认的是「长什么样」，验收的也是「长得像不像」；「点下去会发生什么、旧能力还在不在」没有任何承载物。加上 10:47 开 goal 后 73 分钟自动跑完 S1–S7，自评截图通过即交付 4.0.0，用户 13:27 一用就露出 demo 状态。

**来源审计结论（这是本轮要的答案之一）**

## 四、机制根因（重点）

### 4.1 一条可验证的因果链

**需求源从「用户要完成的任务」被替换成「设计稿」→ 设计稿同时被指定为唯一验收对照 → 截图只能证明「像」，不能证明「能用/旧能力还在」→ 旧能力接线与假入口落在验收盲区 → goal 自主把实施压缩成 73 分钟并自评完成 → 用户成为唯一真实测试者，一用即暴露。**

逐环证据与验证方式：

1. **需求源替换**：`design-book.html:67` 自称「这份就是实现与验收的唯一对照」；`AGENTS.md:15` 规定「界面实现以样张与 shell-spec-final 为验收标准，同一窗口尺寸下截图并排比对，对不上即未完成」。验证：全仓没有「用户任务清单/场景脚本」文件，`plan-4.0.md` 的验收全部以屏为单位（`:92,99,105,112,118,124,130`）。
2. **设计稿承载不了行为**：38 屏是静态 mockup，`shell-full-round1.html:828-847` 的脚本只做切屏，`design-book.html:262-…` 只做 iframe 缩放；图里的心形、菜单、按钮没有 handler。验证：在样张 HTML 里点击「+」「心形」「右键」不会有任何反应；`design-book.html:175` 还把「可交互」定义成「放大不失真、可滚动」，不是可操作。
3. **覆盖清单没有落到可验证项**：`ui-coverage-4.0.md` 有 48 行，但它的列是「现状/样张/分类/4.0 处理」，没有「入口/操作/预期/证据/测试」；`保留换样式`、`照做` 都不是可判定的完成条件。验证：对照当前代码，`ui-coverage-4.0.md:22,23,24`（标签栏/会话恢复/打开文件夹）标「照做/保留」，实际全部缺失；清单从未在 S7 被逐行回查（`plan-4.0.md:130` 的 S7 验收是 38 屏走查）。
4. **实施被自主模式压缩**：10:41 批准 → 10:45 起 S0–S7 → 11:58 出 4.0.0；10:47 用户开 goal 后进入自主运行；`plan-4.0.md:148` 预期「8 个切片，约 10–14 个可验收轮次」，实际 73 分钟内 8 片全出，平均 9 分钟/片。验证：git 提交时间戳；用户 10:47–13:27 无消息。
5. **验证只在截图与数据层**：截图证据在 `design/verify/`（s0–s7 系列），测试只有主进程/数据层 26 个文件，0 个 UI 组件测试；旧 UI 测试 38 个文件随旧 renderer 删除。验证：`find tests`、`git show --stat 7a81036`。
6. **自评通过即交付**：11:59 消息自述「38 屏没有逐屏点一遍」「真机用一两天才是最终验收」，但同一轮已把 goal 标记完成、4.0.0 装进 `/Applications`、合并 main。验证：`7a81036`、`66fce21` 时间与消息；用户 13:27 的反馈。

**这条链的可证伪性**：如果任一环为假，缺口应在交付前暴露。例如——若验收含任务脚本，第 3 环的缺失会在 S1 就被抓到；若用户试运行发生，第 4/6 环会提前暴露；若覆盖清单有「入口/操作/证据」列，第 3 环不成立。三条都不成立，所以链成立。

### 4.2 三条互相竞争的解释，哪条证据更强

**解释 A（工程策略）：从零重写 + 不 import 旧 renderer → 旧能力接线必然丢失。**
- 预测：丢失应集中在与旧渲染层强耦合的「接线型」能力（标签会话、打开文件夹对话框、拖放、多窗口、每标签历史、快捷键、列头排序方向、卡片心形），而视觉/数据/主进程能力应保留。
- 证据：`plan-4.0.md:64-78` 规定新代码不 import 旧 renderer；`7a81036` 一次删除 55 个 renderer 文件（该提交共删除 25,937 行）；7 个 IPC 通道在新 UI 无人调用；丢的正好是这 9 类；主进程 +104 行、Cos/缩略图/HEIC 全部保留。
- 强度：**强**，能解释「为什么丢的是这些、不是别的」。

**解释 B（验收机制）：验收源与生产源同一份静态设计稿，验收方式只有截图，所以行为缺口不可见。**
- 预测：缺口不应被任何交付前环节发现；执行方应能一边自述「没逐屏点」一边标记完成；测试结构应无 UI 交互；缺失项应恰好是「截图上看起来没问题」的那类。
- 证据：`design-book.html:67`、`AGENTS.md:15`、`plan-4.0.md:75,130,135`；26 个测试文件 0 UI 组件测试；11:59 自述「没做到」；用户 88 分钟后发现。
- 强度：**强**，能解释「为什么谨慎没换来保障、为什么缺口能通过验收」。

**解释 C（范围被用户缩小）：用户自己选了「只求外观」，功能变少是预期后果。**
- 预测：用户应知道并接受「功能比旧版少」；计划/交付应明确写出删了哪些。
- 正反证据：支持 C 的只有一句——「只求外观」的选项文字确实写了「4.0 会是一个功能比现在少的版本」。但同一选项也写「功能沿用现在的」，而且：①用户在 B 01:15 自由文本里主动提醒「设计稿可能并未完全呈现出所有功能打算怎么用」，并建议「先回去讨论设计稿」；②执行方 01:28 明确承诺「不新增、**不删任何现有功能**」并列出「标签页会话恢复」等要保留；③`project.md:193` 同样写「不删任何现有功能」；④4.0 的 CHANGELOG 从未列出「删除了多标签页 / 打开文件夹 / 收藏心形」这类变更。所以 C 只能解释「用户对功能少于设计稿有心理准备」，解释不了「执行方自己承诺的现有能力被删且无人验证」。
- 强度：**弱**（只能解释一部分预期，不能解释违约与验收缺失）。

**哪条更强**：A 解释缺口**怎么产生**，B 解释缺口**为什么没被发现**；二者互补。若只能选一条作为「为什么谨慎还失败」的主因，**B 更强**：A 的缺口本来是可以被任务型验收抓住的（3.13.1 的能力清单和旧测试都在），而实际验收序列里没有任何一环检查「旧能力还在不在」；反过来，若 B 成立（验收=截图+自评），即使换一个人重写，同样的缺口仍会通过。A 的代码证据很硬，但它解释的是「丢失的位置」，不是「丢失被放行」的原因。C 的强版本（用户接受删功能）被证据排除，只剩「对功能少于设计稿有心理准备」这一点解释力，不能当主因。

**补充一个更贴近用户问题的解释（B 的具体机制）**：用户要求「把不确定的确定下来」时，执行方确定的是**方案**（38 屏 + 19 条 + 48 项处理表），没有确定**完成判据**（每个能力如何证明还在）。于是「谨慎」全部转化为「静态物更全」，而静态物越全，越容易产生「我已经覆盖了」的错觉——`ui-coverage-4.0.md` 的 48 行就是这种错觉的载体：它列了「标签栏」「会话恢复」「打开文件夹」「右键菜单」「拖入」「多窗口」，每一行都写了「照做/保留」，所以看清单会得出「已经想到并处理了」，但没有任何一行能证明它真的被接上。

### 4.3 为什么「迭代好几轮」还在踩同一类坑

| 轮次 | 交付物 | 自验收 | 用户发现 | 失败维度 |
|---|---|---|---|---|
| 3.9–3.13.1（10-24 21:41–00:42） | Finder 式壳层、19 条确认项 | 00:42 自写 19/19「完成」+ 真机走查 7 项 | 01:04「长得和设计稿不一样」 | 视觉保真 |
| 4.0（10-25 01:11–11:58） | 新 renderer，按 38 屏重写 | 11:59 自评「截图对照 + 26 测试 + build + 装好」，并自述没逐屏点 | 13:27「demo 状态，基础功能都没有」 | 行为可用 |

两轮共同点：**实施都在 goal 自主模式下 1 小时左右完成；验收都是执行方自评；用户都是事后唯一的真实测试者。** 第一轮把「设计稿 vs 实现」的差距当成视觉问题，于是第二轮把「视觉保真」做到位；但「旧能力保留」从来没有进入通过判据，所以第二轮把行为丢了。换一个维度失败，不是同一个 bug 修不好，而是**验收维度始终只有一个**。用户说的「感觉还是 demo 状态」正是「静态物全对、动态全不通」的准确描述。

## 五、下一轮最该先确定什么（按「不确定就会再次做错」排序）

1. **「完成」的定义：用户任务清单 + 每条的通过证据（不是屏）。** 先列 8–12 条真实任务（例：从照片来源进 300 库→打开一套→收藏单张→切到文件夹收藏→取消收藏；打开下载目录→看到视频→双击用系统播放器；打开文件夹→注册新来源→在标签页里打开；重启恢复标签组…）。每条任务定义「操作步骤 / 期望结果 / 证据形式（点击后的截图或测试断言）/ 谁签收」。**没有这条，下一轮仍会用截图自评。**
2. **旧版能力保留清单的逐项决策与回归证据。** 把 3.13.1 的用户可见能力（本报告第一节 18 行可作起点）变成表：保留/替换/删除 + 入口位置 + 期望行为 + 对应测试或截图。这项必须在「批准计划」之前完成，并作为验收的硬门槛（缺一项即不合并）。
3. **验收主体与节点：合并 main 前必须由用户走查一遍任务脚本。** 用户已选「关键节点装给我试」，但 4.0 没执行。下一轮把「预览版装好 → 用户试 N 条任务 → 通过才继续」写成不可跳过的节点；agent 不得在用户未试之前自行把 goal 标完成。
4. **行为规格（设计稿未覆盖的部分）必须先写完再开工。** 设计阶段已有 11 项「文字规格即可」，4.0 从未写；下一轮把这些写成可执行规格（入口、状态、边界、错误提示、快捷键），并且**写不完就不进入实施**。用户 01:15 的原话已经点明这个风险（「设计稿可能并未完全呈现出所有功能打算怎么用」）。
5. **「假入口」判定与确认记录规则。** 明确：画了控件没接线=缺陷；状态栏/菜单只允许写已经能用的能力（`CHANGELOG.md` 的 3.12.2 条目已有前车之鉴）。同时规定确认记录：选项选择与自由文本冲突时以哪个为准、由谁复述一遍确认（4.0 的 B 01:15 回答就是选项+自由文本同时存在的情况，执行方选了对自己方便的一半）。

## 六、我无法判断的

1. **用户当时如何理解「只求外观」。** 该选项文字同时包含「功能沿用现在的」和「会是一个功能比现在少的版本」；用户在同一答复里又提醒设计稿不完整。哪一半是用户的真实意图，只能由用户本人澄清；无论取哪一半，「删掉多标签页/打开文件夹/收藏心形」都需要另行确认，而执行方两种读法都没有做逐项确认。
