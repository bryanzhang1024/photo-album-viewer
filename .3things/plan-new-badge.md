# 套图卡「新入库」标记计划（目标 4.8.0）

状态：已实施完成（4.8.0，S1–S5 全做完，装到 `/Applications`）。2026-10-30
结论：G44 那页切「修改日期」降序，前 23 张带「新」，第 24 张起不带；证据见 `acceptance/evidence/new-badge/`。

| 时间 | 原话 | 转成要求 |

## 二、只读核对：现在为什么看不出来

- 套图列表的排序已经有三项：名称 / 图片 / 修改日期（`CosSetListPage.jsx` 的 `SORT_FIELDS`），「修改日期」默认就是降序，偏好按页面记住（`useCosSort` 的 key 是 `sets:署名ID`）。所以**倒序这一步现在就能做**：排序切到「修改日期」即可，今天入库的排最前。
- 真正的缺口是卡片上没有日期也没有任何标记：`setCardItems` 只给卡片填「名称 + 作品/题材 · 张数」，即使按修改日期排好，也看不出从第几张开始是旧的、哪些是这一批。
- 索引里已经有 `lastModified`（套图目录的修改时间，`CosCatalogService.toSetDto`）随列表下发，所以标记不需要改主进程和索引格式。

## 三、库里的事实（今天实测）

- `300-Cos套图库` 下 G44 共 191 套；最近 7 天（≥10-23）有修改的套图 26 套（应用索引里的数）：G44 23 套（22 套本次新入库 + 1 套「乖乖兽·诺亚」今日改名），另 3 套是 10-26 Machi 版本去重时把图搬进保留版、目录时间被刷新的旧套。
- 也就是说：按「最近 7 天」打标，今天会标出 26 套，其中 23 套就是你要找的这批，3 套是 Machi 的旧套。
- 目录修改时间会被「改名、补元数据、搬图」刷新，所以它约等于「最近被动过」，不等于严格的「首次入库时间」。库里能看到 08-20 有 3,797 套、10-08 有 918 套落在同一小时，都是批量处理留下的痕迹。

## 四、方案（默认口径，等你确认）

| 项 | 口径 |
|---|---|
| 标记 | 套图卡封面**左上角**一个「新」角标（右上角被收藏心形占用） |
| 判定 | `lastModified` 在最近 **7 天**内；与 4.6.0「最近有变化」同一时间口径 |
| 位置 | 三处套图列表（全部作品 / 按署名 / 按角色）统一生效，改在 `setCardItems` 一处 |
| 排序 | 不动。需要倒序时用现有「修改日期」（默认降序），偏好会按页面记住 |
| 不改 | 主进程、索引格式、缓存版本；不加「只看新入库」筛选 |
| 版本 | 4.8.0（新增可见标记，向后兼容） |

不做：不做「未读/已读」这种自己点掉标记的机制；不做精确「首次入库时间」（那要给索引加字段并升缓存版本，见下节退出条件）。

## 五、已知误差与退出条件

- 误差：改名/补元数据的旧套会被标「新」，持续到它最后一次被动过满 7 天。当前会多标 3 套 Machi，1 周后自动消失。
- 如果以后觉得这种误标碍事，升级办法是索引记录 `firstSeenAt`（首次收录时间，缓存版本升到 4、旧记录用 `lastModified` 回填），标记改用 `firstSeenAt`。这条不放进本轮。
