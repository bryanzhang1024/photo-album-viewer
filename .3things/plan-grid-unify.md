# 网格割裂（COS 图库 × 照片来源）· 差异分析与统一计划

状态：计划阶段产物，2026-10-26。只读取证与计划，未改产品代码、未构建、未安装。
取证：`.3things/acceptance/evidence/cos-vs-folder/`（4 张 1280×800 截图 + DOM 实测 `measurements.json` + 复现说明 `README.md`）。
方法：隔离 profile 启动 4.4.1 构建，两个入口指向同一份真实图库（300-Cos套图库，9,591 套），同窗口尺寸截图并测量。

用户原话（2026-10-26）：

> 现在还有一个问题，就是 COS 图库展示的东西和照片来源展示的有出入，网格界面长得不一样，有点割裂。这个问题首先可能要找出到底哪里不一样，然后再看怎么改。先做计划吧，先分析，先找原因之类的

---

## 一、结论（先看这一屏）

同一批 9,591 套图，两个入口是**两套并行实现**，不是"一个界面换数据源"：

- 文件夹侧用的是 4.0 新写的 `VirtualGrid + GridCard`（虚拟滚动、密度三档、排序、收藏、选中）；
- COS 侧沿用旧版 `.cos-grid + .cos-card`（CSS 自动分列、全量渲染 + 分页加载），`cos.css` 只是把 `folder.css` 的卡片文字规则抄了一遍。

所以差异分三层：**列数/卡宽不同（最直观）→ 卡片内容口径不同（名字、次行、封面、张数）→ 页头控件与可做的操作不同（排序、密度、收藏、面包屑、搜索位置）**。

另查到一条独立的代码缺陷，它放大了第一层差异：文件夹网格的默认缩略图密度算错了，没设置过密度的文件夹默认落在"紧凑"档（148px），而 COS 固定 168px。于是 1280 宽下文件夹 6 列、COS 5 列——这正是"网格长得不一样"最刺眼的一处。

## 三、卡片内容口径差异（同一套图，两处显示的东西不同）

| 字段 | COS 侧来源 | 文件夹侧来源 | 证据 |
|---|---|---|---|
| 名字 | `cosset.json` 的 `display_name`，并按丙方案去掉当前署名前缀与末尾作品括号 | 磁盘目录名原样 | `data/cos.js` `describeSet()` / `data/directory.js` `toFolderItems()` |
| 次行 | 作品或类型 + 张数（「原创写真 · 33 张」） | 张数 + 目录修改日期；容器目录则为子文件夹数 + 张数 | `CosSetListPage.jsx:61` / `GridCard.jsx:66-69` |
| 张数 | **递归整棵子树**（套内所有子目录的媒体） | **只算当前层直接图片** | `CosCatalogService.parseSetDirectory()` 的 `visit()` 递归 / `facts.directMediaCount` |
| 封面 | 索引时第一张媒体，单图 | 容器目录 2×2 拼贴（≥3 张样本），不足时向下找 1–2 层 | `GridCard.jsx:12-45` + `FolderCoverService` |
| 收藏 | 卡片上没有入口 | 封面右上角心形（悬停显示，收藏后常显） | `CosSetListPage.jsx` 无 heart / `base.css:631` |
| 排序 | 固定按名称，无控件 | 四字段 + 升降序 + 按文件夹记忆 | `FolderPage.jsx:488-515` |
| 新鲜度 | 索引快照，手动「刷新索引」才更新 | 每次进入实时读 + 监听当前目录（4.4.0） | `CosLibraryService` / `watchDirectory` |

覆盖范围另有一层：COS 只索引 `cos-library-roots-v1.json` 里的根（当前只有 300 一套），照片来源是 `library-sources-v3.json` 另一份注册表（Collection / 1TB-2 / 400 / 600 / Downloads 等）。两者本来就可能不同；本轮核对到 300 这一层数量一致（9,591），所以"有出入"的主体是**同一批图的展示方式**，不是少了一批图。

## 四、根因

1. **4.0 只重写了文件夹侧**。`src/ui/features/folder/` 是新组件，COS 页面从旧版搬了 DOM 和样式（`cos.css`），两套并存。
2. **卡片视觉规则有三份拷贝**：`folder.css`（GridCard）、`cos.css`（cos-card）、`favorites.css`（fav-card）。`tokens.css` 只统一了颜色/字号，没有统一"卡片由哪些元素、多宽、几行"。
3. **两套数据模型没有适配层**：目录快照（一层、直系）与 Cos 目录（一套、递归）直接喂给各自的页面，字段口径差异就漏到界面上。
4. **页头/工具栏按 `location.kind` 分支拼装**，没有"页面工具条契约"：搜索在文件夹页放工具栏、在 COS 页放页头；网格/列表切换和排序/密度只给文件夹页。
5. **默认密度缺陷放大列数差异**：`prefs.js:71-78` 里 `Number(localStorage.getItem(...))`，键不存在时 `Number(null) === 0`，被当成合法的"紧凑"档（148），默认本应是标准档（168）。于是没手动调过密度的文件夹是 6 列，COS 固定 168 是 5 列。
6. **验收口径只对设计稿，没有"两个入口并排"的一致性断言**。CSS 拷贝和字段差异因此一直没被发现。

---

## 五、统一方案

**选定：共用网格与卡片基元（B 方案）。** 把 `GridCard` 升为通用卡片、`VirtualGrid` 升为通用网格，COS 三页（全部作品/按角色/按署名、套图内照片）和文件夹页、收藏页都用同一份；差异只允许出现在"数据来源"（封面是单图还是拼贴、次行模板、能不能收藏），不允许出现在尺寸、字号、间距、页头控件上。

**备选（不推荐）：只改 CSS（A 方案）。** 把 `cos.css` 的列宽/间距改成引用 `tokens.css`，一天内能让"看起来像"，但两套 DOM、两套交互、两套字段口径仍在，下一次改动继续发散；也解决不了"名字/次行/封面/张数不同"。

**最小可合并版本：只做 S1**（修默认密度）。单独交付就能让两处列数、卡宽一致，且不改任何结构；但它只解决"一眼看着不一样"，内容与操作差异都还在。

### 最脆弱的假设

这套方案假设"统一"指视觉与操作一致，不要求两处文字一字不差——因为设计稿本身（`screens/book-02` 与 `book-08`）就画了不同的文本：文件夹卡是完整目录名 + 张数 + 日期，套图卡是清理后名字 + 作品 + 张数。若你要的是"同一套图在两处一字不差"，需要额外一片改数据口径（清理规则套到文件夹模式，或套图卡退回原始名），成本约多半天。

## 六、分步计划

每一步都能独立合并、独立看到效果；S2 之后即使 S3 停下，界面也是统一的。

### S1 · 修默认缩略图密度（bug fix，可单独发 4.4.2）

- 做什么：`prefs.js` 的 `getFolderDensity` 缺省返回标准档 1（键不存在时不再把 `null` 当 0）；补一条单测。
- 用户看到：没手动调过密度的文件夹，1280 宽下从 6 列变回 5 列，和 COS 一致；调过密度的文件夹保持原样。
- 验收：单测覆盖"无键返回 1 / 有键 0、1、2 原样返回"；1280×800 截图里 B 页列数 5、卡宽 190.8，与 A 页一致；`npm test`、`npm run build` 通过，安装到 `/Applications` 后实机看一次两处网格。
- 风险：改变了默认观感。若你更喜欢现在的 6 列，就把标准档改成 148、两边一起变，也是自洽的（见待拍板 1）。

### S2 · 共用卡片与网格（视觉统一，主片）

- 做什么：
  - `GridCard` 提到 `src/ui/components/`，入参改为一个卡片模型（名字、次行、封面节点、收藏、选中、角标），封面由调用方给（目录拼贴 / COS 单图）。
  - `VirtualGrid` 提到 `src/ui/components/`，加 `hasMore/onLoadMore`，COS 的 60/120 分页数据用它渲染。
  - COS 三个页面改用这两个组件；`cos.css` 里的 `.cos-card/.cos-name/.cos-meta/.cos-cover` 与三套 `minmax` 列宽规则删除。
  - 列宽统一走密度三档（148/168/196，窄窗 ≥200）；COS 页面接上同一个密度值。
- 用户看到：A/B 两页、C/D 两页的卡片宽、封面高、圆角、名字与次行基线完全一致；COS 页也能调缩略图大小；滚动行为一致。
- 验收：同尺寸截图 A/B、C/D 并排，卡宽、封面高、字号、行高、圆角逐项一致（DOM 测量差值 ≤0.5px）；9,591 套仍能顺滑滚动（分页加载触发正常）；`npm test`、`npm run build`、安装 + 实机。
- 风险：COS 分页接虚拟滚动是这一片的主要技术点（现有 `useCosPagedList` 60/页、套内 120/页），若接不上就退化为"虚拟网格 + 底部加载提示"，需单独确认。

### S3 · 页头与操作统一（同一套图两处都能做同样的事）

- 做什么：
  - COS 页补面包屑（Cos 图库 › 按署名 › 半眸子）、排序、密度、收藏入口；工具栏的网格/列表切换与搜索对 COS 页按统一规则处理（搜索统一放工具栏，COS 页头的搜索框删掉）。
  - COS 套图页补齐：卡片心形、右键菜单、键盘导航、自动刷新，与文件夹照片层对齐。
  - 状态栏提示按"本页真的能用的键"重新对齐。
- 用户看到：同一套图，不管从哪个入口进，页头控件位置和数量一样，收藏/排序/搜索都能用；状态栏提示一样。
- 验收：两入口的页头控件清单一致；收藏状态两处同步（同一份 favorites）；⌘F 在两类页面都聚焦工具栏搜索；`npm test`、`npm run build`、安装 + 实机。
- 风险：COS 收藏身份要落到现有"按路径收藏"模型（`locations[].relativePath` + rootId），若语义对不上需要先补规格。

### S4 · 收藏页并入同一卡片（收尾，可延后）

- 做什么：`favorites.css` 的 `fav-card`（190px/18px gap 的第三套）改用同一卡片；收藏页数量小，不强制虚拟化。
- 用户看到：收藏页的卡片和另外两处一样宽、一样字号。
- 验收：收藏页与文件夹网格卡片尺寸/字号一致；`npm test`、`npm run build`、安装 + 实机。
- 风险：低。若 S2/S3 已验收，这一片可以等下次一起做。

### 交付口径

- 版本：S1 是 patch（4.4.2）；S2+S3 是 minor（4.5.0）；S4 可并入 4.5.0 或 4.5.1。
- 分支：`codex/cos-folder-grid-unify`。
- 每片按项目规则：测试 → `npm run build` → 安装 `/Applications` → 实机验证 → 截图存档到 `evidence/`。
- 另加一个可复跑取证脚本（把这次的一次性脚本沉淀成 `npm run evidence:cos-grid`），以后每次改完能自动比 A/B 两页的列数、卡宽、字号、页头控件，防止再次发散。

## 七、需要你拍板的四件事（回一句就行，不必逐条选标签）

1. **默认密度**：缺省用"标准"（168，1280 下 5 列，与 COS 一致）还是"紧凑"（148，6 列，现在文件夹的观感）？我建议标准。
2. **次行内容**：保留两个模板（套图「作品 · 张数」，文件夹「张数 · 日期 / 子文件夹数 · 张数」），只统一版式；还是完全统一成一种写法？我建议保留两个模板——设计稿本身就这么画，且两处挑选时需要的信息不同。
3. **操作补齐范围**：S3 只补"看得见的一致性"（排序/密度/收藏/面包屑/搜索位置），还是连同右键菜单、键盘导航、自动刷新一起补齐？我建议一起，否则还是"一处能用一处不能用"。
4. **覆盖范围**：COS 目前只索引 300 一套根，400/600 不在里面；这轮是否只统一界面、不动数据源？我建议不动，覆盖范围另开一项。

## 八、本轮边界

- 不改需求、不改设计稿；设计稿与实现的既有出入（例如设计稿把心形画在次行右侧，实现放在封面右上角且悬停才出现）记录在案，不在本轮顺手改。
- 不动主进程数据层（`CosCatalogService` / 目录契约 / 收藏格式），除非 S3 的收藏身份确认必须小改。
- 不做跨来源全库搜索、多选批量操作（backlog 已记事，不混进来）。
